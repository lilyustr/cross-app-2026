# Лабораторна робота 5: Архітектура Catalog Service та принципи SOLID

Цей проєкт демонструє побудову сервісу каталогу товарів із дотриманням принципів чистої архітектури, патернів проєктування та принципу інверсії залежностей (**DIP** із SOLID).

---

## Архітектура та ключові компоненти

### 1. Абстракція сховища (Interface)
* **`ICatalogStore`** — базовий контракт (Repository), що визначає CRUD-операції над сутностями `Product` (`List`, `GetById`, `Add`, `Update`, `Remove`), абстрагуючи спосіб збереження даних від бізнес-логіки.

### 2. Реалізації сховища (Implementations)
* **`InMemoryCatalogStore`** — збереження каталогу виключно в оперативній пам'яті (на основі внутрішньої колекції). Використовується для швидкого прототипування та модульного тестування.
* **`FileCatalogStore`** — файлове сховище з персистентністю, яке серіалізує та десеріалізує стан каталогу у файл `catalog.json`.
* **`CachingCatalogStore`** — реалізація патерну **Decorator**, що обгортає будь-яку іншу реалізацію `ICatalogStore`. Кешує результати точкових запитів `GetById` у внутрішньому словнику, оптимізуючи повторні звернення.

### 3. Сервісний шар (Service Layer)
* **`CatalogService`** — модуль високого рівня, що містить бізнес-правила (додавання, зміна залишків через `Receive`, валідація існування товару, обробка винятків `InvalidOperationException`).
  * **DIP (Dependency Inversion Principle):** сервіс не залежить від деталей збереження на диску чи в пам'яті, а отримує абстракцію `ICatalogStore` через конструктор (Constructor Injection).
  * **Пошук через делегат `Func`:** реалізовано метод `Find(Func<Product, bool> predicate)`, який дозволяє передавати довільні предикати фільтрації товарів.

### 4. Конфігурація та створення (Composition Root / Factory)
* **`StoreFactory`** — статична фабрика (патерн **Factory**), яка інкапсулює логіку аналізу консольних аргументів (`--file`, `--cached`), підготовку шляхів до файлів та побудову готового дерева об'єктів сховища.

## 💡 Пояснення відкладеного виконання (Deferred Execution)

У коді LINQ-запит:
  var query = source.Where(p => p.Quantity < 10);
не виконується в момент його оголошення, а лише створює дерево виклику. Безпосереднє обчислення відбувається в момент виклику термінальних операторів, таких як Count() або ToList().

Чому два виклики Count() дали різні числа:
1. Перший виклик query.Count() проітерував початкову колекцію source і знайшов 3 дефіцитні товари.
2. Після додавання нового елемента через source.Add(...) другий виклик query.Count() знову заново пройшовся по оновленій колекції source, тому повернув 4.
3. Виклик query.ToList() матеріалізував (зафіксував) результати в окремому масиві в пам'яті, зробивши знімок snapshot незалежним від подальшого очищення source.Clear().

### 3. Порівняння Fluent Syntax vs Query Syntax
* Звіт report-groups реалізовано у двох варіантах: ByUnit (Method/Fluent Syntax) та ByUnitQuerySyntax (Query Syntax).
* Fluent Syntax: компактний, зручний для простих ланцюжків дій та застосування кастомних методів-розширень.
* Query Syntax: читабельніший при складному групуванні (group ... by ... into ...) та з'єднанні кількох джерел даних.

### 4. Замір продуктивності Stopwatch (100 000 записів)
* Без ToList() усередині ланцюжка: 11 ms (Lazy Execution, обробка потоком без зайвого виділення пам'яті).
* З ToList() усередині ланцюжка: 8 ms.
* Висновок: Викликання ToList() посеред ланцюжка змушує матеріалізувати проміжну колекцію в оперативній пам'яті, що при великих обсягах даних створює додаткове навантаження на Garbage Collector (GC).
